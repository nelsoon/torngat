# Security notes carried between chunks

Items found in reviews that a later chunk must enforce.

- **apiserver:**
  - Strip or ignore server-set metadata (uid, cell, generation, etag, timestamps, status) on create/update.
  - Run every `validate()` (ObjectMeta, Scope, specs) at the API boundary. Deserialization alone does not enforce them.
- **IAM (apiserver):**
  - Operations live under a global id and carry only their `target` path. `GET /v1/operations/{id}` must authorize against the scope parsed from `target`.
  - `serve()` refuses plain HTTP off loopback; anything that mounts `router()` directly must provide TLS itself.
- **scheduler:** evaluate claim `selector` CEL in a sandbox with cost/time limits.
- **controller:**
  - Treat agent-reported data (inventory, allocations, status) as untrusted.
  - Always call `NodeStatus::validate()`.
  - Never accept allocations from agents.
- **node identity / join:**
  - A node is its certificate name **and** the public key recorded at join (`platform/nodeidentities/<node>`). Every control RPC must go through `identity::authenticate`; deleting the record revokes the node.
  - TPM policy (`platform/settings/tpm`, default and missing = required): file-key joins are refused when required. TPM keys are only recorded as `tpm` after attestation (EK trusted via `pki/tpm-roots` or a token `ek_sha256` pin, credential activation for the AK, AK certification of a fixed-TPM node key matching the CSR). Admins can change it with `PUT /v1/platform/settings/tpm` (body `{"required": bool}`; admin only).
  - EK trust is one hop: the EK certificate must be signed directly by an anchor in `pki/tpm-roots` (put vendor intermediates there). No revocation checking of EK certificates yet.
  - The controller's own node is enrolled by `init` without attestation (the operator is the trust root).
  - TPM keys (SRK and node key) use no authorization value and are created `noDA`, so they never count towards dictionary-attack lockout; access to the TPM device is the boundary. Without `noDA`, each power loss after the key was used counted as a failed authorization, and a few power cuts in a row locked the node out of its key (found by `image/test/power-loss.sh`). Keys created before this change need re-enrollment. PCR-bound policies come later.
  - The CA key sits on the controller's disk (0600). Move it to an HSM/TPM-sealed store before multi-controller.
  - Certificates live one year and there is no rotation yet; add renewal (same key) before production.
  - The TPM device's descriptor (opened by tpm2-tss without close-on-exec) is inherited by the tools `torngatd` runs (lvm, cryptsetup, losetup, systemctl): root tools that could open the TPM themselves. QEMU is started by systemd, not by `torngatd`, and does not get it. Close it on exec when that can be done without unsafe code.
  - `node.json`, `identity/` and `pki/` are trusted local state: anyone who can write them owns the node.
- **compute:**
  - Each instance is a transient unit `torngat-vm-<uid>.service` (`crates/agent/src/qemu.rs`): its own `DynamicUser`, group `kvm` only, no capabilities, `NoNewPrivileges`, a private `/dev` with `/dev/kvm` only, private IPC and network, `AF_UNIX` only, no D-Bus, `MemoryDenyWriteExecute`, read-only system, memory and task limits, no core dumps, and QEMU's own seccomp sandbox.
  - Disks: QEMU's unit allows no device but `/dev/kvm`. It starts paused; the agent opens the instance's decrypted volumes itself (only mappings of volumes the controller attached to that instance and that it lists) and passes the open files over QMP (`add-fd`, SCM_RIGHTS), then lets the guest run. A unit found still paused (start interrupted) is stopped before its guest ever ran; the agent asks each unit it finds once. QMP answers are untrusted: lines are bounded (1 MiB), connecting, each read and write, and each whole session have timeouts. A QEMU that fails or stalls is asked again only after a wait that doubles up to 5 minutes, so that one instance cannot hold back the agent for the others. Disks added to a running instance are hot-plugged the same way (only volumes attached to it and that it lists); what QEMU answers about its disks only decides where to try, every step is checked by QEMU.
  - The QMP socket is in a directory that the instance's user owns: the agent (root) sends nothing unless the socket's peer is the unit's main process (`SO_PEERCRED`). Better later: a socket made by the agent in a root-owned directory and handed to QEMU.
  - Later: a systemd `SystemCallFilter` allowlist (QEMU's own sandbox is a denylist), `LimitFSIZE` and CPU/IO limits, hiding the rest of the host's file system (only what QEMU needs, read-only), and the names of other units in `/sys`. Checked on a lab VM (`crates/agent/tests/qemu_units.rs`) and in the image (`image/test/instances.sh`).
  - A user id freed by systemd can go to another instance later; `/var/lib/torngat-vm/<uid>/` is chowned again at each start, and the console log of an instance is readable only by its current user and root.
  - Networks will need a socket family filter and device list per unit that allow only what they hand over (tap or vhost file descriptors), not `PrivateNetwork=no`.
  - Console logs of deleted instances are not removed yet, and are not limited in size: before tenants get access.
- **storage:**
  - Pool sizes and capabilities come from agents: only the pool's own node may report them. Reservations are written by the controller only, with compare-and-swap, before a volume is placed.
  - A driver must refuse a volume group or ZFS pool that carries another pool's or cluster's mark.
  - LVM (`crates/agent/src/storage/lvm.rs`, checked on a lab VM by `crates/agent/tests/lvm.rs`): changes only logical volumes named `torngat-<uid>` with the pool's tag; a creation is answered only once the first and last 16 MiB are zeros (`torngat-zeroing` until then); deleting deactivates first, so that a volume in use is never wiped. A tag is no proof: anyone who can run `lvm` on the node can forge one. A group that is not found is never taken as released (it may come back with its mark and volumes). `torngatd` may write only `/etc/lvm/backup` and `/etc/lvm/archive`, not LVM's configuration or devices file.
  - Decrypted volumes are named `torngat-vol-<uid>`; `59-torngat-volumes.rules` keeps udev from probing, linking or activating them (`crates/agent/tests/luks.rs` checks it, with a control). Tools run by hand still can.
  - The agent (`crates/agent/src/storage`) opens a volume only while an instance assigned to its node uses it, and closes every other `torngat-vol-*` mapping, also ones left by an agent that stopped. When storage cannot be read or an entry does not decode, it changes nothing.
  - A driver's device must be a block device at an absolute path; other kinds are refused.
  - The agent asks for a key each time it formats, opens or grows a volume, keeps it zeroed-on-drop, and passes it to `cryptsetup` on standard input. Keys are not in the agent's files or arguments; the kernel holds the open volume's key.
  - `--fake-storage` uses files and loop devices: tests only.
  - Volume status has the pool's name, for operators: hide it from tenants when IAM comes.
  - A volume type or pool name in a stored object may no longer exist, or be another one: compare the uid.
  - Placement order (`crates/controller/src/storage.rs`): pool and `granted_bytes` in the volume's status, then the reservation, then `Placed`; without space both are cleared again. Growth order: the reservation, then `granted_bytes`. Deletion order: blocks, reservation (the pool is always written), the key's tombstone, then the object. The sweep reads a pool before the volumes, so that it never releases a reservation being made. Before reserving, check the pool's uid and that it is not being deleted.
  - A volume whose node is lost cannot be deleted, nor its pool: forced removal comes with node removal.
  - Each agent's assignment stream reads every instance, pool and volume twice a second: one stream per node (a newer one ends the older), at most 32 streams per connection.  If storage objects cannot be read, instances keep flowing and the node is told to ignore the storage lists. An index by node before large clusters.
  - A node releases a pool only once no volume names it and nothing is reserved; it cannot change a pool's allocation unit while it holds volumes; its messages may not hold control, invisible or direction characters (`torngat_api::is_hidden`).
  - A growth that is taken back before it is granted leaves the larger reservation until the volume is deleted.
  - A pool is only removed by the controller, after its node released it, once no volume type lists it and no volume names it.
  - Volume keys (`crates/controller/src/volume_keys.rs`): never made again for a formatted volume or a destroyed uid (tombstone). Tombstones are never removed.
  - Racing creates with one request id can briefly bring a uid back: the object of a placed volume goes only after its tombstone, the undo in `create_volume` is retried, and placement refuses a uid with a tombstone.
  - Instance disks (`crates/controller/src/disks.rs`): a volume is attached to one instance at a time (compare-and-swap on `attached_to`, rechecked on what is written), only once that instance has a node and the volume is on it. A boot disk is used only by its owner, and no instance takes another's. Released when the instance is gone or no longer lists it, and only once its node reports it closed (`open`); the node opens a volume only for an instance that lists it. Disks may be added while an instance runs, removed only while it is stopped. A boot disk is deleted after its instance only if `owner.delete_with_it` and not `delete_protection`; a kept one loses its owner. Nothing is released or deleted while an instance or volume does not decode. Messages in an instance's status name no node or pool.
  - Keys are given by the pool's node, which is enough for local storage. Shared storage must also check that the instance in `attached_to` runs on the caller.
  - Node removal must delete the identity before the node's record, or registering makes the record again as active. Needed before real data: a stolen node cannot be cut off yet.
  - Core dumps are off for the `torngatd` service only, not when it is run by hand.
  - Images (`crates/controller/src/images.rs`): only the image's node may report on it, and only while it imports it. Each reported value (download size, format and size) is written once and bounded (at most the largest volume); `done` is accepted only once the image's volume is ready and formatted. The node gets the key of an image's volume only while it imports that image. Volumes owned by an image are never attached, and cannot be changed or deleted through the volume API. Volumes of an image that is gone are deleted (volumes are read before images, so that a new image's are not).
  - Image URLs are checked by the API for their form only (https, a host, no credentials or fragment). Where they lead is checked on the node, at each address and redirect: before tenants get access, no import may reach private, loopback, link-local or metadata addresses.
  - After a restore, nodes have volumes that the store does not know: the agent must never delete a volume because it is unknown, only when told to.
  - Restoring brings back revoked nodes and destroyed keys, and stops instances made since. Etags start again, so an old one can match by chance. A list of revoked nodes outside the store, and instances that are adopted rather than stopped: later.
  - Backups (`crates/keys/src/recovery.rs`) can only be read with the recovery code, and only be made by the cluster. An old backup is not refused: the operator checks its date.
  - The agent keeps received keys in memory that is erased, and never logs them.
  - A volume's key goes only to the node of its pool while an instance uses it (`attached_to`), the first time too. Its record is kept from then on: a missing key is never made again for a volume that had one, nor for one that is `formatted`. The node reports `formatted` after it formatted the volume (or found it formatted), and nothing clears it.
  - Project keys are named by the project's path: when projects become objects, destroy the key with the project, so that a project made later under the same name does not get it.
  - Every controller needs the platform key file: promotion copies it, with the CA key, over mTLS and only to an attested node. Before multi-controller. Rotation of project and platform keys: not yet.
  - A node formats a device only if its first 16 MiB are zero and it is not `formatted`; never one with something else there. A crash after the key was given but before formatting started is harmless; one during `cryptsetup luksFormat` can leave something that is neither blank nor LUKS, and the volume unusable (it held nothing yet: delete it).
  - Volumes and request id records have no limit per project, and the records never expire: before tenants get access.
  - An older version that changes an object drops fields that it does not know: before rolling upgrades.
- **CI:** third-party actions are pinned to commit SHAs; keep them pinned when updating.
